# PayPerView Main Backend ↔ AI Service integration map

**Audit date:** 2026-11-22  
**Scope:** Existing Express/Mongoose backend, the sibling `Desktop\AI` FastAPI service, and the current frontend API calls.  
**Audit rule:** This map is based on the mounted backend routes and callers, the AI Service route/Pydantic definitions and live OpenAPI document, plus a live local health/readiness and authenticated request check. It does not imply that every feature below has had a full business-data end-to-end test.

## Local service and evidence

- The AI Service is configured for port `8001`. Its documented local start command is `uvicorn app.main:app --reload --host 127.0.0.1 --port 8001` from the AI Service directory.
- At audit time, `http://127.0.0.1:8001/health` and `/ready` both returned HTTP 200. Readiness reported the expected Gemini, JWT, backend, service-key, and Chroma checks as configured.
- The live `GET /openapi.json` listed the endpoint groups and schemas below. `POST /api/v1/ai/intelligence/language/detect` also succeeded using the Main Backend's current AI client and configured service key; it returned Arabic detection with `UNICODE_SCRIPT_HEURISTIC`.
- The AI Service source audited was `C:\Users\Jebril\Desktop\AI`. The sibling `Desktop\PayPerView AI` checkout shares its repository base but lacks the newer intelligence route files; the running OpenAPI matches the expanded `Desktop\AI` source.
- Local `.env` files contain credentials. Their values were not included in this document.

## Authentication and service boundary

| Call type | Actual authentication | Identity and ownership boundary |
| --- | --- | --- |
| Internal campaign, review, finance, recommendation, moderation, and language analysis | `X-Service-Key` matching the AI Service's `AI_SERVICE_API_KEY` | Only the Main Backend calls these routes. The backend authenticates the web user, scopes database queries to the owner/role, and builds the payload. The AI Service does not independently bind these payloads to a tenant identity. |
| Chat thread and message routes | `Authorization: Bearer <Main Backend JWT>` | AI Service validates the shared JWT and revalidates the user/role through the Main Backend profile endpoint. Thread IDs are scoped to the token's user ID in the AI Service; the Main Backend also owns its local thread mapping and checks local ownership. |
| `GET /health`, `GET /ready`, and OpenAPI | No auth in the current AI Service | Keep this listener internal. Readiness is not an authenticated business API and does not make a Gemini request. |

The browser calls only the Main Backend. The service key is never part of a frontend request. Main Backend records and authorization remain authoritative; AI responses do not execute payments, refunds, withdrawals, moderation decisions, campaign approvals, or ledger changes directly.

## Main Backend → AI Service contracts

Every listed JSON intelligence/review request uses `X-Service-Key`. Unless stated otherwise, the timeout is from the current backend client, no retry is applied to the POST, and the backend maps connection/upstream failures to a controlled unavailable/bad-response result. The AI Service validates request bodies with Pydantic. The Main Backend validates responses before using them.

Saves `aiReview.result`, `score`, `feedback`, and `reviewedAt`, then maps approved/rejected/manual-review results to the campaign state. Missing/invalid response or AI outage routes to manual review. The advisory AI response does not replace backend campaign checks. |

## Available, not connected to a backend workflow

The live AI Service also exposes these authenticated internal routes, but the current Main Backend does not call them:

| AI endpoint | Current state and missing dependency |
| --- | --- |
| `POST /api/v1/ai/intelligence/content/review` | Exists and accepts the structured text/content review request. The current integrated submission worker calls `/api/v1/ai/submissions/review` instead. No separate workflow needs a second review call today. |
| `POST /api/v1/ai/intelligence/videos/analyze` and `GET /api/v1/ai/intelligence/videos/{analysis_id}?tenantId=...` | Exists for a trusted video upload, async job status and result. The backend has no trusted video-byte/frame source or Main Backend-owned job/status link. Do not make the service fetch creator-supplied URLs or expose the service to browser clients. |

Other blocked or limited capabilities are absent at the data-source layer, not missing HTTP routes: AI-assisted eligibility before view accrual needs a separately agreed pre-accrual contract and a safe call point; backup anomaly/storage prediction need actual backup and capacity telemetry; richer payment fraud needs provider evidence; full demographic audience analysis is not supported by available data. AI does not perform payment/withdrawal operations.

## Audit findings and backend changes

1. `AI_SERVICE_BASE_URL` is now the canonical base setting. `AI_SERVICE_URL` remains a compatibility alias for this local `.env`. `AI_SERVICE_ENABLED`, bounded shared/per-operation timeouts, and a common HTTP transport are implemented. Hardcoded hosted-service fallbacks were removed.
2. Intelligence, campaign review, submission review, and chat now use the shared transport for base URL selection, auth headers, timeouts, and safe upstream errors. Analysis POSTs are not retried; chat retries only idempotent list/read calls.
3. The frontend wallet path `POST /api/v1/ai/wallet/intelligence` is now a backend compatibility route alongside `POST /api/v1/wallet/intelligence`. Both paths share brand authorization, request validation, and response behavior.
4. `docs/openapi.yaml` was regenerated from the mounted router inventory and validated. The wallet alias has the same BRAND role, request schema, response schema, and documented failure statuses as the original route.
5. The live health/readiness and language-detection calls passed. An opt-in live integration test now covers those checks without contacting Gemini or writing Main Backend records. Database-backed business workflows and authenticated browser-to-backend-to-AI chat still require suitable test users and data for end-to-end verification.

## Runtime configuration guidance

- Prefer `AI_SERVICE_BASE_URL` in the backend. For a backend process on the same host as this local service, use `http://127.0.0.1:8001`. A container must use a reachable service/container hostname or the platform's host-gateway address; `127.0.0.1` inside the backend container means that container itself.
- Set `AI_SERVICE_API_KEY` only in server environments and keep it identical to the AI Service's configured service key. Never send it to the frontend.
- Use a separate timeout setting with a bounded value; keep operation-specific caps for fast recommendation/view/earnings calls and the longer content-review deadline.
- `AI_SERVICE_ENABLED=false` must make optional analyses return an explicit unavailable state or a safe workflow fallback. Critical campaign/submission review must route to manual review rather than success.
- Keep `/health`, `/ready`, `/docs`, and `/openapi.json` on an internal network or protected ingress in deployed environments. Do not expose the local service publicly as part of the frontend architecture.
